Исследовательский ML-прототип для диагностики технического состояния СВЧ-модулей по временным рядам температуры, вибрации и электрических параметров.

Проект демонстрирует полный цикл решения задачи:

1. генерация экспериментальных сигналов;
2. оконная обработка временных рядов;
3. извлечение признаков;
4. обучение и сравнение ML-моделей;
5. оценка качества без смешивания экспериментов;
6. преобразование предсказаний в уровень риска и рекомендации;
7. отображение результатов в интерфейсе Streamlit.

## Статус проекта

Проект является исследовательской работой.

Модели обучаются на сгенерированных данных, созданных с учётом физически интерпретируемых режимов работы оборудования, шумов, дрейфа сигналов, выбросов, пропусков и пересечения похожих технических состояний.

Полученные метрики показывают качество модели на сгенерированном наборе данных и не являются подтверждением промышленной точности на реальном оборудовании.

## Диагностируемые состояния

Модель классифицирует семь состояний:

1. нормальная работа;
2. перегрев;
3. ухудшение системы охлаждения;
4. повышенная вибрация;
5. дисбаланс;
6. износ механического узла;
7. комбинированная неисправность.

## Исходные сигналы

Для каждого эксперимента формируются следующие временные ряды:

- `temperature_chip` — температура кристалла;
- `temperature_case` — температура корпуса;
- `vibration_x` — вибрация по оси X;
- `vibration_y` — вибрация по оси Y;
- `vibration_z` — вибрация по оси Z;
- `current` — потребляемый ток;
- `voltage` — напряжение;
- `load` — уровень нагрузки;
- `fan_speed` — скорость вентилятора.

## Набор данных

Параметры текущей конфигурации:

- 7 классов;
- 80 экспериментов для каждого класса;
- 560 экспериментов всего;
- продолжительность эксперимента — 60 секунд;
- частота дискретизации — 100 Гц;
- размер окна — 5 секунд;
- шаг окна — 2,5 секунды;
- 500 измерений в одном окне;
- 12 880 окон после оконной обработки.

Сгенерированные датасеты не хранятся в Git-репозитории. Репозиторий содержит код и конфигурации для их воспроизводимого создания.

## Генерация сигналов

В генераторе моделируются:

- индивидуальные особенности экземпляров оборудования;
- случайный измерительный шум;
- постепенный дрейф параметров;
- кратковременные выбросы датчиков;
- пропуски отдельных измерений;
- слабовыраженные неисправности;
- переходные режимы;
- пересечение признаков похожих состояний;
- комбинированные неисправности.

Такая генерация усложняет задачу по сравнению с классификацией идеально разделимых классов, но не заменяет реальные измерения.

## Оконная обработка

Каждый эксперимент разбивается на пересекающиеся окна.

Оконная обработка позволяет классифицировать не весь эксперимент целиком, а отдельные временные интервалы. Это приближает систему к сценарию непрерывного мониторинга оборудования.

Окна одного эксперимента сохраняют общий идентификатор эксперимента.

## Извлечение признаков

Из каждого окна рассчитывается более 100 признаков.

### Статистические признаки

- среднее значение;
- стандартное отклонение;
- минимум и максимум;
- квантили;
- диапазон значений;
- линейный тренд;
- скорость изменения сигнала.

### Температурные признаки

- разность температур кристалла и корпуса;
- длительность превышения температурных порогов;
- отношение температуры к нагрузке;
- отношение температуры к скорости вентилятора;
- интегральный индекс температурной нагрузки.

### Вибрационные признаки

- RMS;
- пиковое значение;
- пик-фактор;
- частота пересечения нуля;
- суммарная вибрация по трём осям;
- интегральный индекс вибрационной нагрузки.

### Частотные признаки

- доминирующая частота;
- спектральный центр;
- ширина спектра;
- энергия в частотных диапазонах;
- соотношение низкочастотной, среднечастотной и высокочастотной энергии.

### Интегральные признаки

- `thermal_stress_index`;
- `vibration_stress_index`;
- `combined_stress_index`.

## Разбиение данных

Обучающая и тестовая выборки разделяются по целым экспериментам.

Окна одного эксперимента не могут одновременно находиться в обучающей и тестовой выборках.

Это ограничивает утечку данных, которая могла бы возникнуть при случайном разделении сильно похожих соседних окон.

Приблизительно 20% экспериментов каждого класса используются как тестовая выборка.

## Модели

В проекте сравниваются следующие алгоритмы:

1. Logistic Regression;
2. Random Forest;
3. Extra Trees;
4. HistGradientBoosting.

Логистическая регрессия используется как базовая линейная модель.

Основной итоговой моделью является `Extra Trees`.

## Метрики

Основная метрика проекта — `F1-macro`.

Она рассчитывает F1 отдельно для каждого класса, а затем усредняет результаты. Благодаря этому качество сложных состояний не скрывается за общей долей правильных ответов.

Результаты текущего эксперимента:

| Модель | Accuracy | F1-macro |
|---|---:|---:|
| Logistic Regression | 0.7400 | 0.7200 |
| Random Forest | 0.8595 | 0.8643 |
| Extra Trees | 0.8672 | 0.8714 |
| HistGradientBoosting | 0.8377 | 0.8444 |

Значения относятся только к текущей версии синтетического набора данных и используемой схеме разбиения.

## Продуктовая логика

Выход классификатора преобразуется в прикладной результат:

    техническое состояние
            ↓
    уровень риска
            ↓
    рекомендуемое действие

Система предназначена не только для отображения названия класса, но и для поддержки принятия инженерного решения.

## Пользовательские роли

### Оператор

Получает:

- текущее состояние оборудования;
- уровень риска;
- предупреждение;
- рекомендуемое действие.

### Инженер-техник

Получает:

- диагностированное состояние;
- уровень риска;
- приоритет проверки узлов;
- рекомендуемую последовательность действий.

### ML-инженер

Получает:

- информацию о данных;
- используемые признаки;
- сравнение моделей;
- метрики;
- матрицу ошибок;
- анализ значимости признаков;
- техническую информацию о предсказании.

Детальные вероятности классов и внутренние ML-метрики не являются основной информацией для оператора.

## Основные ограничения

1. Используются синтетические, а не реальные стендовые данные.
2. Результаты зависят от правил и параметров генератора.
3. Пока не проведена внешняя валидация на другом источнике данных.
4. Не исследована переносимость модели между разными типами оборудования.
5. Автоматические тесты пока не входят в завершённую часть проекта.
6. Сгенерированные датасеты, обученные модели и отчёты не хранятся в репозитории.
7. Проект не является готовой промышленной системой мониторинга.

## Направления развития

- сбор реальных стендовых данных;
- сравнение синтетических и реальных распределений;
- адаптация модели к конкретному оборудованию;
- оценка неопределённости предсказаний;
- обнаружение неизвестных состояний;
- временная валидация;
- автоматизированное тестирование пайплайна;
- мониторинг дрейфа данных;
- контейнеризация и развёртывание;
- интеграция с системой сбора телеметрии.

## Назначение проекта

Проект показывает, как знания в области СВЧ-техники и эксплуатации электронного оборудования могут быть объединены с методами машинного обучения для создания системы предиктивной диагностики.

Основной результат проекта — не только обученная модель, но и воспроизводимый end-to-end пайплайн от генерации сигналов до инженерной рекомендации.
